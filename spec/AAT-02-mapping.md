# Разбор AAT-02: инварианты и алгоритм → модель

Источник: draft-niyikiza-oauth-attenuating-agent-tokens-02 (октябрь 2026),
https://www.ietf.org/archive/id/draft-niyikiza-oauth-attenuating-agent-tokens-02.txt.
Прочитаны разделы 3.1–3.2, 4 (инварианты I1–I6), 8 (алгоритм проверки), 9.8 (отзыв).
В -02 алгоритм проверки — раздел 8; раздел 7 — proof of possession.

Модель на момент разбора: `AatLean/Chain.lean`, коммит `89f8d73`.

## 1. Главное

1. **Т1 на шаге 4 — это доказательство корректности таблицы 4 спецификации.**
   §4.1 прямо разделяет два отношения: структурное `c_child ⊑ c_parent`, которое
   исполняют верификаторы, и семантическое «каждое значение, допустимое ребёнку,
   допустимо родителю». Спецификация утверждает (без доказательства), что
   структурное отношение корректно (sound) относительно семантического, но не
   полно: часть семантически верных сужений отвергается. Это ровно наша пара
   `narrowsB` / `Narrows`. Т1 с семантическим `Narrows` = механизированное
   доказательство этого утверждения §4.1.
2. **`verify_complete` на шаге 4 станет ложной** — по замыслу спецификации, а не
   из-за ошибки. Полнота возможна только относительно структурных правил, не
   относительно `Narrows`.
3. **Отзыва в спецификации нет** (§9.8: «This document defines no revocation
   mechanism»). Входы алгоритма §8: chain, trust_anchors, tool, args, pop_jwt —
   снимка отзывов R среди них нет. Т5 в нынешнем виде выходит за спецификацию.
4. **Т2 следует из Т1.** Алгоритм проверяет аргументы вызова только против листа
   (шаг 6b). «Вызов удовлетворяет ограничениям всех звеньев» получается из
   проверки листа плюс Т1 по цепочке. Это и есть содержательная Т2.
5. **Спецификация сама делает три утверждения «по индукции» без доказательства**
   (заметки к §8 и шаг 5). Их можно доказать в Lean — прямой вклад к тексту
   черновика:
   - каждый `del_max_depth` ≤ `MAX_DELEGATION_DEPTH` (из шагов 3i, 4g);
   - каждый `exp` ≤ `iat + MAX_TOKEN_LIFETIME` (из 3h, 4h, 4j);
   - `len(chain) = leaf.del_depth + 1` (шаг 5 назван «defense in depth»; следует
     из 3c и 4d).

## 2. Инварианты → модель

| Инвариант | Что требует (§4) | В модели сейчас | Куда |
|---|---|---|---|
| I1 Delegation Authority | `derived.iss == jwk_thumbprint_uri(parent.cnf.jwk)`; ребёнок подписан ключом держателя родителя | `Linked`: `child.issuer = parent.holder` — та же форма, если `holder` = отпечаток `cnf.jwk` | Т3 (подпись) + переименовать `holder` в `cnf` |
| I2 Depth Monotonicity | `del_depth` = родитель + 1; ≤ `parent.del_max_depth`; ≤ свой `del_max_depth`; ≤ `MAX_DELEGATION_DEPTH`; `del_max_depth` не растёт | нет | **новая теорема** (глубина) |
| I3 TTL Monotonicity | `exp ≤ parent.exp`, `exp > now`, `exp > iat`, `iat ≥ parent.iat`, `iat ≤ now + MAX_IAT_SKEW`, `exp ≤ iat + MAX_TOKEN_LIFETIME` | нет | Т4, расширить с «действительна в момент t» до всего I3 |
| I4 Capability Monotonicity | `tools(child) ⊆ tools(parent)`; для каждого инструмента `constraints(child) ⊑ constraints(parent)` по таблице 4 и правилам ключей `"*"` / required / optional | только первая строка (`narrowsB` по именам) | шаг 4, Т1 |
| I5 Cryptographic Linkage | `child.par_hash == SHA-256(parent signing input)` | нет; `Linked` связывает по имени — дыра из ревью раунда 2 | новое поле `parHash`, хэш как абстрактная инъективная функция |
| I6 Proof of Possession | PoP подписан ключом `leaf.cnf.jwk` | нет | вместе с запросом в `verify` |

## 4. Ответы на открытые вопросы из ревью

| Вопрос | Ответ по тексту |
|---|---|
| Есть ли `del_depth` / `del_max_depth` (R-1) | да, I2 |
| Монотонность срока (R-1) | да, I3: `child.exp ≤ parent.exp`, `child.iat ≥ parent.iat` |
| Корень: `del_depth = 0`, нет `par_hash` (R-1) | да, шаги 3c, 3d |
| `Linked` по имени, а не по токену (раунд 2) | спецификация закрывает это через I5 `par_hash` (§4.6: «grant-context substitution») |
| `cnf` / proof-of-possession (раунды 1–3) | да, I6 и шаг 7 |
| `aud` (раунд 2) | да, шаг 6c; производный токен может сузить `aud`, но не снять |
| Циклы (R-1) | шаг 2c: повтор `jti` → DENY |
| JCS (R-1) | только для сравнения `hta` с `args` в PoP (7f), не для ограничений |
| `typ` (R-1) | да, `typ = "aat+jwt"`, шаги 3a, 4a |
| Длина цепочки / DoS (раунд 2) | `MAX_DELEGATION_DEPTH` (≥ 8), `MAX_TOKEN_SIZE`, `MAX_CHAIN_SIZE` |
| Реестр корней — список или отображение (R-1) | `trust_anchors`: множество пар (издатель, ключ) |
| Пустой ключ `""` (раунд 2) | `root.iss` обязан быть URI (3k); пустая строка не URI |

## 5. Решения, которые нужны от Ерасыла

1. **Т5 (отзыв).** В AAT-02 отзыва нет. Варианты:
   (а) убрать Т5 и R из сигнатуры;
   (б) оставить как расширение по §9.8: статус-лист только для корней, Т5 =
   «корень принятой цепочки не отозван»;
   (в) оставить как есть — тогда это не модель AAT.
   Предложение: (б) — §9.8 прямо называет этот механизм.
2. **`verify_complete` на шаге 4.** Предложение: полнота относительно
   структурных правил таблицы 4 (`verify` = allow ⇔ все структурные правила
   выполнены), корректность относительно семантики — Т1.
3. **Новые теоремы.** Добавить в список:
   Т6 — глубина (I2, шаг 5); Т7 — три утверждения «по индукции» из §8;
   `aud` (шаг 6c) — отдельно или внутри Т2. Предложение: добавить Т6 и Т7,
   `aud` — в Т2.
4. **Что остаётся вне модели.** Предложение: байтовый уровень (размеры, `alg`,
   `typ`, `crit`, дубликаты JSON, форма `cnf.jwk`) — допущение «токены
   разобраны и прошли синтаксические проверки». Подписи и хэш — идеальные
   (допущение 1 + инъективность хэша).
5. **Объём шага 4.** Предложение: сначала `wildcard`, `exact`, `one_of`,
   `range` и правила ключей `"*"` / required / optional; `all` / `any` /
   `not_one_of` / `contains` / `subset` — вторым проходом.
6. **Финальная сигнатура `verify`.** По §8 входы: chain, trust_anchors, tool,
   args, pop_jwt, плюс now и состояние σ (nonce, PoP `jti`). Утверждённое
   условие Т1 называло `verify(σ, t, R, trustedRoots, req)`. Если R уходит
   (решение 1а), сигнатура меняется — по условию утверждения Т1 это добавление
   параметров, Т1 не переутверждается; если добавляются `tool`, `args`,
   `pop_jwt` вместо `req` — то же самое.

## 6. Неоднозначности текста

Явных противоречий в разделах 4 и 8 не найдено. Места, где текст опирается на
неформальное рассуждение:

- §4.1: «those rules are sound with respect to it» — утверждение без
  доказательства. Проверяется Т1 на шаге 4.
- §8, Notes: два требования «hold by induction and need no step of their own»;
  шаг 5 — «defense in depth», то есть по замыслу тоже следствие. Проверяется Т7.
- §4.5, таблица 4: «Every other pair is invalid and MUST be rejected» —
  исчерпывающая таблица; для модели это значит, что `⊑` задаётся перечнем
  случаев, а всё остальное — `false`.

Сверить со списком неоднозначностей Давлятшина (шаг 3), прежде чем считать
этот список новым.
